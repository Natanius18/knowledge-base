# Code smells

## 1. Long Method
**Что это:** Метод растянут на кучу строк — больше 10-20.

**Почему плохо:** Трудно читать, как длинный текст без абзацев. Легко запутаться, где что.

**Как починить:** Разбей на маленькие методы. Каждый делает одну простую вещь. Например, вместо одного большого — вызови 3-4 коротких.

## 2. Large Class
**Что это:** Один класс делает всё: хранит данные, считает, проверяет — как чемодан с посудой и одеждой.

**Почему плохо:** Когда меняешь — рискуешь сломать всё. Нарушает правило "один класс — одна задача".

**Как починить:** Выдели части в новые классы. Например, расчёты — в отдельный класс.

## 3. Primitive Obsession
**Что это:** Используешь простые типы (строка для email, число для денег) вместо специальных объектов.

**Почему плохо:** Нет проверок: email может быть "abc", деньги — отрицательные. Повтор кода везде.

**Как починить:** Создай класс Email или Money с проверками внутри. Передавай их, а не сырые строки/числа.

## 4. Duplicate Code
**Что это:** Один и тот же кусок кода копипастится в 2+ местах.

**Почему плохо:** Меняешь в одном — забываешь в другом, ошибки множатся.

**Как починить:** Выдели в общий метод или класс. Один раз пишешь — везде используешь.

## 5. Switch Statements
**Что это:** Огромный switch или if-else на типы/статусы.

**Почему плохо:** Добавляешь новый тип — переписываешь всё. Код растёт.

**Как починить:** Используй полиморфизм: каждый тип — свой класс с методом. Или карту (Map) с функциями.

## 6. Feature Envy
**Что это:** Метод А часто лезет в данные класса Б (a.getB().doThis()).

**Почему плохо:** Метод "завидит" чужим данным, нарушает границы классов.

**Как починить:** Перенеси метод в класс Б. Пусть Б сам работает со своими данными.

## 7. Comments
**Что это:** Код засыпан "// объяснениями".

**Почему плохо:** Комменты устаревают, код не понятен сам по себе. Хороший код говорит за себя.

**Как починить:** Удали комменты. Улучши имена переменных/методов. Разбей на методы.

## 8. Dead Code
**Что это:** Неиспользуемые методы, переменные, классы.

**Почему плохо:** Мусор отвлекает, код кажется сложным.

**Как починить:** Удали без жалости. IDE покажет, что не используется.

## 9. Data Clumps
**Что это:** Всегда передаёшь вместе имя, фамилию, email как отдельные параметры.

**Почему плохо:** Запутанно, легко перепутать порядок.

**Как починить:** Сделай класс Person с этими полями. Передавай один объект.

## 10. Long Parameter List
**Что это:** Метод с 4+ параметрами.

**Почему плохо:** Трудно запомнить, что куда. Легко ошибиться при вызове.

**Как починить:** Сгруппируй в объект (как в Data Clumps) или сделай параметры полями класса.

## 11. Divergent Change
**Что это:** Один класс приходится часто менять по разным причинам.

**Почему плохо:** Класс начинает отвечать сразу за много вещей, и любое изменение цепляет лишнее.

**Как починить:** Раздели обязанности по разным классам. Например, отдельно поиск, отдельно вывод, отдельно сохранение.

## 12. Shotgun Surgery
**Что это:** Маленькое изменение в одном месте тянет правки в кучу файлов и классов.

**Почему плохо:** Очень легко что-то забыть и сломать. Любая мелочь становится дорогой.

**Как починить:** Собери связанные куски ближе друг к другу. Перенеси логику в одно место.

## 13. Parallel Inheritance Hierarchies
**Что это:** Появились две иерархии классов, которые всё время растут вместе.

**Почему плохо:** Добавил один класс в одной иерархии — надо не забыть добавить похожий в другой.

**Как починить:** Подумай, можно ли убрать одну из иерархий или заменить её отдельным объектом-типом.

## 14. Inappropriate Intimacy
**Что это:** Два класса слишком много знают друг о друге и лезут в чужие внутренности.

**Почему плохо:** Изменишь один класс — второй тоже может сломаться.

**Как починить:** Убери лишнюю связь. Оставь только нужные методы, а остальное спрячь.

## 15. Message Chains
**Что это:** Длинные цепочки вызовов вроде `a.getB().getC().getD()`.

**Почему плохо:** Код хрупкий. Если что-то поменяется в середине цепочки, придётся править много мест.

**Как починить:** Спрячь детали за отдельным методом. Пусть объект сам отдаёт нужное значение.

## 16. Middle Man
**Что это:** Класс почти ничего не делает, а только передаёт вызовы дальше.

**Почему плохо:** Лишний слой усложняет код, но пользы почти нет.

**Как починить:** Убери лишнюю прослойку или перенеси поведение туда, где оно реально нужно.

## 17. Lazy Class
**Что это:** Класс слишком маленький и почти ничего не делает.

**Почему плохо:** Он только создаёт шум и усложняет понимание.

**Как починить:** Удали его или объедини с другим классом.

## 18. Data Class
**Что это:** Класс хранит только поля и простые геттеры/сеттеры, без своей логики.

**Почему плохо:** Такой класс сам ничего не умеет и превращается просто в мешок с данными.

**Как починить:** Добавь туда поведение, которое связано с этими данными, или убери класс, если он не нужен.

## 19. Speculative Generality
**Что это:** Код сделан "на будущее", но сейчас не нужен.

**Почему плохо:** Лишняя сложность появляется раньше времени и мешает работать.

**Как починить:** Удали ненужные абстракции, методы, поля и классы. Добавишь потом, когда реально понадобится.

## 20. Incomplete Library Class
**Что это:** Внешняя библиотека не даёт нужной функции, и ты начинаешь городить обходные решения.

**Почему плохо:** Код становится неудобным, сложным и зависимым от чужих ограничений.

**Как починить:** Оберни библиотеку своим классом, чтобы спрятать неудобства. Если надо, замени библиотеку на более подходящую.

## 21. God Class
**Что это:** Один класс взял на себя слишком много: хранит данные, считает, решает, управляет.

**Почему плохо:** Такой класс трудно понять и страшно менять.

**Как починить:** Раздели его на несколько классов по задачам.

## 22. Spaghetti Code
**Что это:** Код без нормальной структуры: всё перепутано, много переходов и хаоса.

**Почему плохо:** Его тяжело читать и почти невозможно аккуратно менять.

**Как починить:** Упростить логику, разбить на методы и классы, убрать лишние связи.

## 23. Functional Decomposition
**Что это:** В ООП-коде всё написано как в старом процедурном стиле: много функций, мало нормальных объектов.

**Почему плохо:** Объекты не помогают, код расползается и хуже расширяется.

**Как починить:** Перенести данные и поведение в классы, а не держать всё в отдельных функциях.

## 24. Deficient Encapsulation
**Что это:** Поля и методы сделаны слишком открытыми, хотя это не нужно.

**Почему плохо:** Любой код может лезть внутрь и ломать объект.

**Как починить:** Спрячь внутренности, оставь только нужные публичные методы.

## 25. Swiss Army Knife
**Что это:** Класс пытается уметь вообще всё, как швейцарский нож с кучей лишних функций.

**Почему плохо:** Интерфейс становится тяжёлым и непонятным.

**Как починить:** Оставь только нужные возможности, остальное вынеси в отдельные классы.

## 26. Cyclic Dependency
**Что это:** Классы или модули завязаны друг на друга по кругу.

**Почему плохо:** Менять и тестировать такой код очень неудобно.

**Как починить:** Разорвать круг, выделить общий слой или интерфейс.

## 27. Boolean Blindness
**Что это:** Метод принимает `true/false`, и без контекста непонятно, что означает этот флаг.

**Почему плохо:** Легко перепутать смысл и вызвать метод неправильно.

**Как починить:** Заменить флаг на отдельные методы или понятный объект/enum.

## 28. Magic Number
**Что это:** В коде торчат странные числа вроде `17`, `3600`, `42` без объяснения.

**Почему плохо:** Неясно, что это значит, и потом сложно менять.

**Как починить:** Вынести в константы с нормальными именами.

## 29. Null Check
**Что это:** Повсюду проверки на `null`.

**Почему плохо:** Код разрастается и становится шумным.

**Как починить:** Стараться не передавать `null`, использовать пустые объекты, Optional, нормальные значения по умолчанию.

## 30. Mutable Data
**Что это:** Данные постоянно меняются в разных местах.

**Почему плохо:** Легко случайно сломать состояние.

**Как починить:** Делать данные неизменяемыми, где это возможно, и менять их только в одном месте.

## 31. Inconsistent Names
**Что это:** Одни и те же вещи называются по-разному.

**Почему плохо:** Чтение кода превращается в угадайку.

**Как починить:** Договориться об одном стиле именования и придерживаться его.

## 32. Inconsistent Style
**Что это:** В коде всё оформлено по-разному: скобки, отступы, порядок, стиль вызовов.

**Почему плохо:** Код выглядит неряшливо и тяжело читается.

**Как починить:** Использовать единый форматтер и правила стиля.
